# 对象的引用类型
---
- **强引用（Strong Reference）**：只要存在强引用，直到OOM也不会回收。如`Object obj = new Object`。
- **软引用（Soft Reference）**：内存充足时不回收，内存不足（将要发生OOM）时才会进行回收。常用于实现内存敏感的高速缓存。
- **弱引用（Weak Reference）**：无论内存是否充足，只要发生GC就会被回收。
- **虚引用（Phantom Reference）**：目的是为了在对象被回收时收到一个系统通知。常用于配合引用队列跟踪堆外内存的释放（如`ByteBuffer`的`Cleaner`）。
# 垃圾判定算法
---
## 引用计数法
为每一个对象添加一个引用计数器。每有一个对该对象的引用，计数器加一；引用失效时，计数器减一。计数为0时可以进行回收。
**缺点**：无法解决依赖循环问题，导致内存泄漏。因此Hotspot不使用该方法。
## 可达性分析算法
以一系列被称为GC Roots的根对象作为起点，从这些节点出发根据引用关系向下搜索，走过的路径称为“引用链”。如果一个对象与任何GC Roots都没有引用链相连，说明该对象不可达。
可以作为GC Roots的对象：
1. **虚拟机栈中栈帧的局部变量表中引用的对象**（如方法参数、局部变量）。
2. **方法区中静态字段引用的对象**（如`public static Object obj = new Object();`）。
3. **方法区中常量引用的对象**（如`public static final`修饰的引用）。
4. **本地方法栈中JNI引用（Native方法）的对象**。
5. **Java虚拟机内部的引用**：
	1. **基本类型的Class对象**。
	2. **常驻的异常对象**（如`NullPointerException`、`OutOfMemoryError`等）。
	3. **系统类加载器**。
6. **所有被同步锁（synchronized）持有的对象**。
> [!tip] 二次标记和finalize()自救
> 在判断对象不可达后，如果对象重写了finalize()且未被执行过，对象会被放入F-Queue队列，等待一个低优先级的Finalizer线程执行。如果对象在finalize()中将自己的引用(this)赋值给某个引用变量，在第二次小规模标记中就能避免被回收。
> > [!warning] 
> > 任何对象的finalize()只会被虚拟机调用一次。因其执行时间不可控，已经被废弃，不能用于资源释放。
# 垃圾回收算法
---
## 分代收集假说
- **弱分代假说**：绝大多数对象都是朝生夕灭的（即大多数对象创建后很快就不再使用）。
- **强分代假说**：经过越多次垃圾回收的对象，就越难死亡。
- **跨代引用假说**：跨代引用相对于同代引用来说只占极少数。
## 三种算法

|      | 标记-清除算法(Mark-Sweep) | 标记-复制 (Copying)                      | 标记-整理 (Mark-Compact)                     |
| ---- | ------------------- | ------------------------------------ | ---------------------------------------- |
| 原理   | 标记存活对象、回收未标记对象      | 将内存分成两块，<br>回收时将存活对象复制到另一块，<br>清空原区域 | 标记存活对象，<br>将标记的对象全部移至一边，<br>清理边界外的区域     |
| 优点   | 实现简单、不需要移动对象        | 没有内存碎片、按序分配、效率高                      | 没有内存碎片、不会浪费内存空间                          |
| 缺点   | 会产生大量内存碎片           | 存在内存浪费、存活率高时复制开销大                    | 移动对象需要更新所有引用，<br>STW（Stop The World）时间较长 |
| 适用区域 | CMS的老年代             | 新生代（Appel 式 8:1:1）                   | Serial Old、Parallel Old的老年代              |
## 垃圾回收的范围
• `Minor GC(Young GC)`：只回收新生代（Eden + S0/S1）。
• `Major GC(Old GC)`：只回收老年代（目前只有 CMS 收集器有单独的老年代收集行为）。
• `Mixed GC`：回收整个新生代以及部分老年代（G1 收集器特有）。
• `Full GC`：回收整个 Java 堆和方法区。
## 回收过程
设最初使用的Survivor区为S0。
1. 新对象不断在Eden分配。
2. 当Eden满时，触发`Minor GC`：
	1. 扫描Eden和S0。
	2. 标记存活对象。
	3. 将存活的对象复制到S1。
	4. 将存活对象的年龄+1（记录在对象头中）。
	5. 清空Eden和S0。
	6. 交换S0和S1的角色。
3. **晋升机制**：
	1. **长期存活的对象**：年龄达到阈值（默认15）时进入老年代。
	2. **大对象直接晋升老年代**：大小超过一定阈值的对象直接进入老年代，如很长的字符串或很大的byte数组。避免在Eden和Survivor之间进行大量内存复制。
	3. **内存分配担保**：Minor GC存活的对象无法完全放入目标Survivor区时，通过内存分配担保借用老年代内存。
	4. **动态对象年龄判定**：Survivor区中，如果存在一个最小年龄N，使得从1到N的对象大小总和超过了阈值（默认50%），则年龄大于等于N的对象晋升为老年代。
**相关参数**：
- `-XX:MaxTenuringThreshold`：晋升老年代年龄阈值，默认为15（CMS、G1），最大值为15。
- `-XX:PretenureSizeThreshold`：大对象直接进入老年代的阈值。适用于Serial和ParNew。

# 三色标记法
---
传统的垃圾收集器，在标记过程中需要全程**STW（Stop The World）**，所有用户线程都会挂起，此时对象图是静态的，遍历标记不会出错。
但随着内存的不断增大，STW时间越来越长，为了缩短STW，现代垃圾收集器引入了**并发标记**，让GC标记线程和用户线程同时进行，这带来了新的问题：在遍历对象图时，用户线程也可能在修改引用关系。
## 三色标记
- **白色**：**未访问**。可达性分析开始时，所有对象都是白色。分析结束仍为白色代表**不可达**，为垃圾对象。
- **灰色**：**已经被访问过，但对象内部的引用字段还有未扫描的**。表示标记正在进行的中间状态。
- **黑色**：**已经被访问过，且对象内部的引用字段都已经扫描完成**。表示安全存活的对象。
## 标记过程
1. **初始化**：只有GC Roots是**灰色**的，其他堆对象都为**白色**。
2. **并发标记**：从灰色对象中取出一个，将内部引用字段指向的对象标记为**灰色**，然后将自身标记为**黑色**。
3. **完成**：当堆中没有灰色对象时，标记结束。此时黑色为存活对象，保留；白色为垃圾对象，清理。
## 并发问题
当用户线程在并发标记阶段修改引用时，可能出现多标和漏标的问题。
### 多标（浮动垃圾）
对于已经标记为灰/黑色的对象，突然删除所有指向该对象的引用，但该对象以及向下的对象这一轮都不会被回收。
**解决方法**：无。这些对象称为**浮动垃圾**，等待下一次GC清理。
### 漏标（对象消失）
存活的对象被当成垃圾对象误杀，漏标条件：
1. **插入引用**：黑色对象插入了白色对象的引用。
2. **删除引用**：所有灰色对象的相关直接或间接引用都被删除。
**解决方法**：
3. **增量更新（CMS收集器）**：破坏条件1。当黑色对象插入白色对象的引用时，通过写后屏障将黑色对象重新标记为灰色。在并发标记结束后，进入重新标记阶段（STW），再次扫描这些灰色对象。
4. **原始快照 （SATB, Snapshot At The Beginning）（G1收集器）**：破坏条件2。在并发标记开始时保存对象图的快照，后续标记时按照快照的可达性进行标记。当灰色对象删除白色对象的引用时，通过写前把删除的引用记录下来。在重新标记阶段（STW），记录的白色对象会扫描并标记为黑色，在下一轮GC中清理。
# 垃圾收集器
---
## CMS（Concurrent Mark Sweep）
### 核心运行阶段
1. **初始标记**（STW）：仅标记GC Roots直接关联到的对象和年轻代指向老年代的对象，耗时极短。
2. **并发标记**：从GC Roots关联的对象开始，遍历标记整个对象图，耗时最长。
3. **重新标记**（STW）：修正并发标记阶段因为用户线程导致标记变化的对象，耗时比初始标记稍长。
4. **并发清除**：清理没有被标记的垃圾对象。
### Concurrent Mode Failure
并发清除时，老年代的空闲空间不足以放下新分配的对象。
此时STW，并退化为使用单线程的 Serial Old 收集器进行传统的 Full GC。
### 缺点
1. **CPU敏感**：并发标记和并发清除阶段，CMS默认启动的回收线程数为(CPU核心数 + 3) / 4，会占用部分CPU资源。
2. **浮动垃圾**：并发清除阶段，用户线程的业务逻辑还在产生新的垃圾对象，这些对象不会被清理，只能在下一次GC清理。因此不能满了才回收，必须预留空间给新对象。
3. **内存碎片**：CMS使用**标记-清除**算法，会产生大量内存碎片，可能导致Concurrent Mode Failure。
**相关参数**：
- `-XX:CMSInitiatingOccupancyFraction`：CMS触发的老年代内存占用率阈值。
## G1（Garbage-First）
JDK9开始，G1成为了默认的垃圾收集器。
### 内存区域
G1逻辑上依然保留了Eden、Suvivor、Old等分代概念，但物理上不再连续。
G1将堆内存划分为约2048个大小相等的区域（Region），每个Region的大小在1MB ~ 32MB间（必须是2的幂次方）。
Region除了可以是Eden、Suvivor、Old，还可以是**Humongous Region**。
**Humongous Region**：用于存放超过0.5个Region大小的超大对象，如果对象超过了一个Region的大小，会寻找连续的空白Region区作为Humongous Region区存放。
### Remembered Set
在扫描一个Region时，为了知道是否存在其他Region对该Region的引用，但又不能全堆扫描一遍，因此每个Region都维护一个**Remembered Set**。
**Remembered Set**：记录其他Region指向本Region的引用。
当引用变更时，写屏障会将跨Region的引用记录到Card Table，再同步到RSet。
**缺点**：RSet占用内存较大。
